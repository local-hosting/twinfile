# Situations and scenarios

A place describes the site. A situation describes a story any place can bind. A scenario runs that story against one place. {{ className: 'lead' }}

Unit kinds are `place`, `event`, `situation`, `scenario`, and `mixin`. Mixins are the packs `with:` attaches. Events are timetables a scenario can include (arena ships `events/game-day`).

## Shared situations {{ anchor: false }}

Fourteen shared situation units ship in the private [`@doppler-group/twinfile-simulator`](https://github.com/twinfile/simulator) catalog. A place opts in through a mixin or a local plan. The situation declares `phases` and the roles it `expects`. Hazard label → unit mapping: [`hazard-catalog.yaml`](https://github.com/twinfile/spec/blob/main/conf/hazard-catalog.yaml). Lantern-style map pins: [`hr-marker-crosswalk.yaml`](https://github.com/twinfile/spec/blob/main/conf/hr-marker-crosswalk.yaml).

`twinfile/severe-weather:1.0.0`:

```yaml
twinfile: 1
kind: situation
name: severe-weather
version: 1.0.0
stability: stable
phases:
  - watch
  - warning
  - all-clear
expects:
  shelter:
    kind: space
    min: 1
  exit:
    kind: opening
    min: 2
  outdoor:
    kind: space
    min: 0
```

Your `plans/*.yaml` maps those role names to space and opening ids on this site. See [Author a place](/author#plans).

## Live controls vs offline runs {{ anchor: false }}

On a built **place**, `image.meta.placeType.controls` is the button surface (`signal:trigger` / situation pulses). Prefer that in product UI — not a separate Twinfile per button. The host **player** advances **`clock:`** and publishes the same IN messages as those buttons (patch module bus). **`use.runner`** stays the offline **ENTRYPOINT** for `twin run`, frozen verify, and **`question:`** answers (JSON Lines stdout) — same timeline, different sink ([world time](https://github.com/twinfile/spec/blob/main/doc/glossary.md#world-time-clock-timeline-player-runner)).

## A scene run {{ anchor: false }}

A run is a scene payload under a **story**: `story/examples/<story>/scenes/<scene>/run.yaml`. `from:` is the place ref. `steps[].copy` pulls situation and event units (use typed refs). `args:` are the run inputs. `use.runner` names the solver.

`story/examples/shop-visit/scenes/shop-shelter-at-cap` (shop's only reference run):

```yaml
role: run
from: twinfile/place/shop:0.2.0
id: shop-shelter-at-cap
name: Shelter at capacity
version: 1.0.0
stability: example
steps:
  - copy: twinfile/situation/severe-weather:1.0.0
clock:
  starts_at: 2026-06-12T18:00:00-07:00
  duration: PT30M
  step: PT5M
args:
  occupancy: 180
  target_role: shelter
use:
  runner: npm:@twinfile/runner-hydraulic@^0
```

```bash
twin run story/examples/shop-visit/scenes/shop-shelter-at-cap
twin verify story/examples/shop-visit/scenes/shop-shelter-at-cap --frozen
```

Frozen runs pin `expected/digest.txt`. `twin check --strict --frozen` fails when the built digest moves. Compose order is place, then events, situations, plan bindings, scenario patches, and `args:` ([composition](https://github.com/twinfile/spec/blob/main/doc/build/composition.md)).
