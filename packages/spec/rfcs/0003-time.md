# RFC 0003 — clock, tracks, schedules, and feeds

## Summary

Give scenarios a real clock, and let places describe what changes over that clock: values that vary (tracks), recurring windows that occupy parts of the place (schedules), and recorded sensor readings (feeds).

Status: Proposed
Created: 2026-11-05

## Motivation

Before this RFC, time in a scenario was a set of offsets from an unnamed T0. That covered "the warning fires at halftime" but not:

- daylight, which needs a calendar date and a location;
- deliveries, cleaning, and sampling runs that repeat on a weekly pattern;
- sensor readings that arrive after they were measured, so "what was true" and "what was known" differ.

Runners also had to invent their own feed formats (the river example read a two-column CSV with implied 5-minute steps).

## Specification

Normative prose: [`doc/place/time.md`](../doc/place/time.md). Summary:

- **Scenario `clock`** — `starts_at` (RFC 3339 with an explicit offset), `duration`, `step` (ISO 8601 durations). `t` is seconds since `starts_at`.
- **`tracks:`** place layer — `solar` (sun elevation from `place.location`), `curve` (daily `HH:MM` points, wrapping midnight), `feed` (a sensor or gauge property), `schedule` (1 while a schedule is active). `interpolate`: `linear`, `step`, or `none`.
- **`schedules:`** place layer — `when` in an opening-hours subset, optional `uses` (space, opening, route, marker), optional `variance.start` for seeded lateness, optional **`activeWhen`** on a numeric track (e.g. solar daylight).
- **Feed rows** — JSON Lines using `sensor.v1` field names (`device_id`, `observed_property`, `value`, `unit`, `quality`) with RFC 3339 `observed_at` and optional `available_at`.
- **Runner input** gains `timeline: { clock, units, samples[] }`, precomputed at every clock step so runners in any language can read it.
- **`place.location`** — `{ lat, lng }`, required only by `solar` tracks.
- **`sensors[].properties`** — the properties a sensor reports, separate from `observes` (what it watches).
- **`sensors[].simulate` / `gauges[].simulate`** — generate feed rows from the scenario clock (see normative doc); optional CLI export to JSON Lines.
- **Phase starts** — situation time args (`releaseAt`, …) map to **`phaseStarts`** on the runner timeline.

Tracks and schedules are arrays of `{ id }`, so they compose with the existing merge rules: a base place defines them, a derived place or scenario patch overrides by id.

## Conformance

- Schema vectors for tracks, schedules, feed rows, and scenario clocks (`section: time`).
- New category `time` (`conf/time/cases.json`): curve interpolation and midnight wrap, schedule windows by weekday, feed truth versus knowledge, quality gaps, and solar elevation ranges. Implementations MUST pass these with an absolute tolerance of 1e-6 (ranges for solar).

## Drawbacks

- Simulated tracks that evolve over time (storms, crowds) are not covered. They are expected to be generated once into a feed file, which keeps runs reproducible.
- `variance` is defined by a specific hash so independent implementations agree; changing it later changes results.
- Schedule windows cannot cross midnight in v1; split them into two rules.

## Alternatives

- **Per-place fixed tick rate.** Rejected: the right resolution depends on the question (evacuations in seconds, daily foot traffic in hours), so the scenario owns `step`.
- **Iterator-only runner API.** Rejected: map scrubbing needs random access, so every sample is a pure function of `t`.
- **Tracks for schedules.** Rejected: a delivery occupies specific spaces and openings; a 0/1 signal alone loses that. Schedules can still expose a track.
